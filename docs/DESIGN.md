# Absolute Zero 1.0.0 — 設計・保証の境界

## 1. 明示された仕様を維持した部分

盤面は5×5〜7×7、駒は1〜9。移動は直交方向に数字と同じ距離、着地は占有セルのみ、途中の駒は飛び越す。移動元を空にし、移動先を絶対差へ更新する。差0は空セル。駒0枚を勝利、それ以外で合法手0を行き止まりとする。

数字を盤面サイズに合わせて縮める、空マスへの移動を追加する、新しい駒を毎手追加する、対角移動を加える、といった変更はしていない。

## 2. 実装上追加した仕様

航路60面、最初の4面の学習用固定問題、3段階のデイリー、自由生成、ヒント、無制限のUndo/Redo、記録、テーマ、効果音、PWA、共有コードを追加。制限時間は導入していない。

星は最短性ではなく、全消し・ヒント不使用・巻き戻し/再開不使用の記録。デイリーの切り替え基準は日本時間UTC+9。全利用者で同じ盤面になるよう、端末現地の午前0時を使っていない。

## 3. 状態と権限

`core.js` はDOM・Storage・ネットワークを持たない。盤面は一次元配列で、`index = row * size + column`。0が空き、1〜9が駒。

`apply()` は入力盤面を変更せず、新しい配列を返す。UIは`apply()`を経由して手を採用する。保存からの復帰も初期盤面と履歴を再生して再構築する。未検証の保存盤面をそのまま信頼しない。

`app.js` が表示、入力、保存、音を担当。ヒント探索Workerは候補経路を返すだけで、盤面を自動で変更しない。ヒントを使っても、実行はプレイヤーが行う。途中状態の上書き読み込みと記録削除には画面上の確認を要求する。

## 4. ルールから分かる制約

### 4.1 数字の上限と盤面

n×n盤面内の直交最大距離はn−1。したがってn以上の数字は自力で動けない。しかし着地点としては使用できる。たとえば「4」が4マス先の「5」に着地すると、同じマスに「1」が残る。これにより動けない駒を利用できる。

### 4.2 占有セル集合は縮小する

移動先は必ず既存の占有セルである。移動元は空になる。したがって、プレイ中に空セルへ新たな着地点を「作る」ことはできない。できるのは、既存の駒を着地点として残し、その数字を変えること。

### 4.3 数字の合計の偶奇は不変

aとbを合成したときの合計の減少量は、

```text
a + b - |a - b| = 2 * min(a, b)
```

常に偶数。初期合計が奇数の盤面は全消しできない。合計が偶数であることは必要条件であって十分条件ではない。

### 4.4 最後の一手

最後は同じ数字aの2枚であり、同じ行または列に、距離aで存在しなければならない。単に同数のペアが残ればよいのではない。

### 4.5 必ず有限手で停止する

合法手ごとに駒数は1枚または2枚減る。初期k枚からは高々k−1手で全消しまたは行き止まりになる。1枚だけ残った状態は行き止まり。この性質により探索に循環はない。

## 5. 解ける盤面の逆生成

空盤面から、次の2種類の逆操作だけを採用する。

**同数ペアの追加**：空セルsとtを選ぶ。sから数字aでtへ合法的に跳べる距離を確保し、両セルへaを置く。順方向の`s → t`で空盤面へ戻せる。

**既存の差cの分割**：駒cのあるセルtと空セルsを選ぶ。sからtまでの距離をaとし、1≤a≤n−1かつ1≤b≤9、`|a-b|=c`となるbを選ぶ。sへa、tへbを置く。順方向の`s → t`で元のcへ戻せる。

各逆操作の順方向の手を記録し、最後に逆順へ並べる。各逆操作が戻せるため、生成手順の長さについての帰納法で、最終初期盤面には全消し経路がある。さらに全手順を`apply()`で実行し、実際に0枚になることをチェックしてから採用する。

初期盤面の合計を偶数にするだけの生成ではない。幾何的に合法な経路を持つことまで保証する。

**保証しないもの**：解の一意性、最短解、プレイヤーが任意に選んだ合法手の後の可解性、人間が感じる難しさ、市場での新規性、すべてのシードで異なる盤面になること。

## 6. ヒント探索の結果を混同しない

- `solved`：全消しまでの経路を発見し、再検証できた。
- `unsolvable`：探索を完了し、全消し経路がないと確認できた。
- `limit`：時間またはノード数の上限に達した。可解性は不明。

初期証明経路と、探索で得た証明経路の中間状態をキャッシュする。経路キャッシュに一致しない局面はWorkerで探索する。通常UIの上限は220,000ノード、約4.5秒。時刻チェックは128ノード単位のため、厳密に4.500秒で停止するハードリアルタイム保証ではない。

状態変更時に古いWorkerを停止し、リビジョン番号でも遅延応答を無効化する。古い盤面向けのヒントが新しい盤面へ適用されないようにする。

## 7. 再現性と版管理

コード例：`AZ1-J12`、`AZ1-D20260907-2`、`AZ1-F7-EXAMPLE`。

`AZ1` は単なるアプリ表示バージョンではなく、問題生成アルゴリズムとシード解釈の識別子である。将来、生成順序、乱数処理、通常問題の設定を変える場合は、同じAZ1コードから違う盤面が生まれないようにする必要がある。AZ2への変更時には旧版の解釈を残すか、明示的な互換性方針を設ける。

乱数は固定された32bit演算を使い、日付はUTC時刻へ9時間を加えて決める。暗号学的乱数が必要な設計ではない。自由演習の新しいシード作成には利用可能なら`crypto.getRandomValues()`を使用する。

## 8. PWAと更新

初回インストール時に版ごとの全ファイルをキャッシュする。キャッシュキーはアプリ名・登録スコープURL・版を含む。削除するのは同じスコープの旧版キャッシュだけ。他のゲームのキャッシュやStorageを一括削除しない。

ナビゲーションにも、インストール済み版のHTMLを優先する。新しいHTMLと古いJS/CSSを混ぜない。新しいService Workerは自動で強制有効化せず、ユーザーが設定で更新を選択したときに、進捗を保存して再読み込みする。

ネイティブのPWAインストール・HTTPS環境でのサービスワーカー実動は、この配布の自動UIテスト対象ではない。モックによるキャッシュスコープ・オフライン応答テストと、実ブラウザの配信試験は区別する。

## 9. 非目標と未確定事項

アカウント、サーバー、対戦、課金、ランキング、不正防止、広告、アクセス解析、外部LLMは実装していない。ユーザーの用途・公開先・収益化方針としてそれらを仮定したものではない。

クライアントには生成と解答検証のコードが含まれる。技術的に解答を取り出すことを防ぐ設計ではない。端末時計やローカル記録を改変できるため、競技用のスコア保証もない。

実機での楽しさ、長期の難易度バランス、片手操作の細かな感触はプレイ評価が必要。コード量や盤面数だけで「必ずハマる」とは言わない。
